# Filmoteka — отчёт о тестировании и интеграции Kinopoisk API Unofficial

**Дата:** 24.11.2026  
**Статус:** тест получения карточек успешен; проект интеграции для согласования и реализации.  
**Адресат:** основной агент-архитектор Filmoteka / агент разработки Codex.

## 1. Контекст и решения владельца проекта

Filmoteka — сайт личных библиотек и оценок произведений. Сохранять существующий стек Django + PostgreSQL и архитектуру модульного монолита. Перед внесением изменений изучить актуальные модели, маршруты и документы KB проекта; имена сущностей ниже являются предложением, а не требованием создать дубликаты уже имеющихся моделей.

- Вместо TMDB выбрать Kinopoisk API Unofficial (`https://kinopoiskapiunofficial.tech`) как основной внешний источник. Это сторонний сервис, не официальный API Яндекса.
- Русскоязычный интерфейс и русскоязычные метаданные — приоритет.
- Использовать только основной постер `posterUrl`; не импортировать `coverUrl`, `logoUrl`, галереи и дополнительные изображения в MVP.
- Создать единый локальный каталог произведений, общий для всех пользователей. Повторно использовать импортированные данные, не создавать копию карточки на каждого пользователя.
- Сохранять личные оценки, комментарии, статусы просмотра, видимость и права доступа отдельно от каталога. Не менять согласованную систему оценки и правила доступа к профилям.

## 3. Контракт внешнего API

Базовый URL: `https://kinopoiskapiunofficial.tech`. Заголовки: `X-API-KEY: <секрет>` и `Accept: application/json`.

| Назначение | Метод |
|---|---|
| Поиск | `GET /api/v2.1/films/search-by-keyword?keyword=<query>&page=1` |
| Альтернативный поиск с фильтрами | `GET /api/v2.2/films?keyword=<query>&page=1` |
| Полная карточка | `GET /api/v2.2/films/{id}` |
| Съёмочная группа | `GET /api/v1/staff?filmId={id}` |
| Сезоны (необязательно, отдельная функция) | `GET /api/v2.2/films/{id}/seasons` |

Для MVP выбрать один метод поиска, предпочтительно `search-by-keyword`, не вызывать оба при каждом запросе. В v2.1 нормализовать `films[]` и `filmId` в общий DTO; в v2.2 — `items[]` и `kinopoiskId`. Перед реализацией сверить схему и параметры выбранного метода, сделать контрактный smoke-тест с живым API без вывода секрета. Не смешивать схемы поиска и полной карточки. Для запроса передавать параметры HTTP-клиента, а не вручную конкатенировать строку URL.

Ограничения: документация указывает 25 запросов/сек. на пользователя и возможные отдельные лимиты методов. Реальная суточная/общая квота зависит от тарифа; проверить в кабинете. Не закладывать произвольную цифру в бизнес-логику.

## 4. Архитектура и пользовательский сценарий

**Local-first + cache-aside + lazy import.** Разделить результаты поиска и постоянный каталог. Не выкачивать весь каталог или полные карточки всех кандидатов.

### 4.1. Поиск при добавлении в библиотеку

1. Пользователь вводит название в форме добавления. Предлагаемые параметры: минимум 3 символа, debounce 500–700 мс, отмена устаревших запросов на клиенте. Поиск по Enter доступен сразу для валидного запроса.
2. Браузер обращается только к Django, например `GET /api/catalog/search?q=Интерстеллар&page=1`. Ключ поставщика остаётся на сервере. Маршрут адаптировать к существующему проекту.
3. Django нормализует запрос (Unicode, регистр, пробелы, ё/е для поиска; оригинальный текст сохраняется для отображения) и ищет в локальном каталоге PostgreSQL по русскому/оригинальному названию и году. Можно использовать `pg_trgm` и индекс нормализованных названий; внедрять при необходимости.
4. Проверяет общий кеш поисковой выдачи по `(provider, normalized_query, page, filters)` с TTL. При актуальном кеше возвращает локальные совпадения и кешированных кандидатов, объединённых по внешнему ID. Если кеша нет/он устарел, запрашивает одну страницу внешнего API. Локальное совпадение само по себе не означает полноту выдачи: пользователь должен иметь возможность найти одноимённое произведение, например через «Искать в Кинопоиске» или внешний поиск при отсутствии актуального кеша.
5. Сохраняет компактные результаты поиска в кеш. Карточки из выдачи содержат название, год, тип, ID, доступные жанры/рейтинг и превью или заглушку. Не запрашивать staff/details отдельно для каждого результата и не скачивать все постеры. Для внешних превью до импорта использовать только разрешённый способ показа; если права не подтверждены — заглушку. Не отправлять поставщику ID пользователя, оценки и комментарии.
6. Пользователь выбирает нужный результат. На явное добавление (или отдельное открытие подробной карточки, если это требуется существующим UX) выполняется импорт полной карточки только выбранного ID. Не делать импорт при каждом вводе символа.

### 4.2. Импорт карточки

1. Проверить наличие `(provider='kinopoisk_unofficial', external_id)` и полноту/актуальность записи. Если уже импортирована — переиспользовать её без внешних запросов.
2. Если отсутствует: запросить карточку и staff, нормализовать поля. Обработать отсутствие постера/съёмочной группы отдельно. Возвращать понятный статус неполных данных; сетевой сбой staff не равен пустому списку режиссёров.
3. Сохранить карточку и связь с внешним идентификатором через транзакцию и уникальные ограничения; не держать транзакцию БД открытой во время HTTP-запросов. Дедуплицировать одновременный импорт одного ID с блокировкой/lease на общий ключ вне длительной SQL-транзакции, проверять запись повторно после получения блокировки. Аналогично объединять одновременные cache-miss поиска.
4. Один постер загружать только для импортируемого произведения, если это разрешено условиями использования. Хранить файл через Django Storage (`media/catalog/kinopoisk/<id>/poster.<ext>`), в PostgreSQL — путь, источник, размеры, формат и статус. Вариант хранения ссылок/заглушки предусмотреть при отсутствии прав. Не хранить бинарные картинки в таблицах БД. Атомарная публикация файла, проверка MIME и декодирования, ограничение размера и пикселей, HTTPS, контролируемые хосты и редиректы, защита от SSRF; не передавать API-ключ на CDN.
5. Создать личную запись пользователя со ссылкой на локальный `work_id`. Если карточка уже есть, не импортировать её повторно. Повторное добавление одного произведения тем же пользователем идемпотентно. При сбое обязательных данных не создавать ошибочную личную запись; дать повторить действие. Необязательный сбой постера не блокирует добавление.

### 4.3. Повторные обращения и обновления

- Открытие библиотеки, оценка, профиль, рекомендации по локальным данным: без обращения к внешнему API.
- При одинаковом запросе и действующем кеше — 0 внешних поисковых запросов, независимо от пользователя.
- Повторный импорт одного ID с полноценной карточкой — 0 запросов.
- Предлагаемые начальные TTL (конфигурируемые, не требования поставщика): поисковая выдача 24 ч, успешный пустой ответ 10 мин, карточка 30 дней. Ошибку API не кешировать как «ничего не найдено». Устаревшие карточки не удалять и не блокировать их чтение; обновление по явному запросу или ограниченной management command, с учётом квоты. Автоматический планировщик не обязателен для MVP.
- `lastSync` поставщика и локальные `fetched_at`/`last_success_at` хранить отдельно. Не считать дату поставщика датой локальной загрузки.
- При отсутствии сети возвращать локальные/устаревшие результаты с предупреждением о неполноте, не обнулять сохранённые сведения.

### 4.4. Расход квоты

Обычный первый поиск одной страницы + импорт одного нового произведения: 1 запрос поиска + 1 карточка + 1 staff = 3 API-запроса, плюс отдельный HTTP-запрос постера (его учёт в квоте проверить). Сезоны, следующие страницы, повторные попытки и обновления увеличивают расход. Повторное добавление из готового локального каталога — 0. Не обещать 0 для нового поискового текста, даже если нужная карточка уже сохранена: внешняя выдача по новому запросу может понадобиться.

## 5. Модель данных (адаптировать к существующей схеме)

| Сущность | Ответственность |
|---|---|
| `Work` | Каноническая карточка, внутренний PK, названия, годы, тип, описание, жанры, страны, длительность, внешние рейтинги, nullable-поля |
| `ExternalWorkId` | FK Work, provider, external_id; уникальная пара provider/external_id; IMDb ID при наличии |
| `Person` / `Credit` | Идентификатор персоны источника, русское и оригинальное имя при наличии; FK Work, роль, порядок выдачи; несколько режиссёров, одна персона может иметь несколько ролей |
| `PosterAsset` (или поля Work) | Один активный основной постер, путь, URL источника, ширина/высота, MIME, статус и время загрузки |
| `CatalogSearchCache` | Нормализованный запрос, provider, фильтры, страница, компактный payload/IDs, дата и срок действия |
| `LibraryEntry` | FK пользователя и Work, личные статусы/оценки/комментарии; уникальная пара user/work, если соответствует действующей модели |

Не объединять разные произведения по совпадению названия, года или изображения; использовать внешний идентификатор и внутренний PK. При будущем добавлении поставщиков сопоставление по IMDb ID проверять на конфликты. Импортированные сведения не должны перезаписывать пользовательские оценки. Внешний рейтинг отдельно от рассчитанного личного рейтинга Filmoteka.

### 5.1. Маппинг

| Поле API | Локальное назначение |
|---|---|
| `kinopoiskId`, `imdbId` | Внешние идентификаторы |
| `nameRu`, `nameOriginal`, `nameEn` | Русское название, оригинальное название и английский вариант (если есть) |
| `year`, `startYear`, `endYear` | Год релиза, период выпуска |
| `type`, `serial`, `genres[].genre` | Формат, признак сериала, жанры; проверить наличие полей в живом ответе |
| `description`, `shortDescription`, `slogan` | Описания/слоган при разрешении на использование |
| `countries[].country` | Страны |
| `filmLength`, `ratingAgeLimits` | Длительность, возрастная классификация |
| `ratingKinopoisk`, `ratingImdb`, `ratingKinopoiskVoteCount`, `ratingImdbVoteCount` | Внешние оценки и количество голосов |
| `posterUrl` | Единственный основной постер |
| `lastSync`, `webUrl` | Обновление источника и ссылка на источник |
| `staffId`, `nameRu`, `nameEn`, `professionKey` (staff) | ID персоны, имена, роль |

Хранить стабильные машинные ключи модели и DTO, переводить подписи в UI, не использовать русские ключи тестового JSON как контракт API. `DIRECTOR` отделять от режиссёров дубляжа. Для людей без русского имени сохранять ID и исходное имя, если оно есть, не придумывать перевод; в UI — согласованный fallback (оригинальное имя с отметкой или «нет русского имени»). Отсутствующие названия, типы и роли не выдумывать. Для аниме использовать наличие жанра «аниме» как отдельный признак, не заменяя формат фильма/сериала. Не выводить сотни актёров на компактной карточке: хранить список, отображать несколько первых с возможностью раскрыть остальные. Для постеров `object-fit: cover` в контейнере 2:3, не растягивать изображение; placeholder если отсутствует. Иностранный язык изображения допустим, поскольку фильтра языка нет.

## 6. Реализация и безопасность

- Выделить адаптер `KinopoiskProvider`, нормализатор DTO и сервис каталога (`search`, `get_or_import`, `refresh`); адаптировать текущий интерфейс TMDB, если он уже существует. Не размещать HTTP-логику в шаблонах/моделях/браузере. Не добавлять Redis/Celery или отдельный микросервис без необходимости; для MVP достаточно существующего Django/PostgreSQL, общего кеша и Django Storage.
- Настройки: `KINOPOISK_API_KEY`, `KINOPOISK_BASE_URL`, таймауты, квоты и TTL, переключатель политики хранения изображений. Секрет в окружении, `.env.example` только с пустым значением. Перевыпустить ранее раскрытый ключ, не помещать его в код, git, логи, URL и отчёты.
- Таймауты HTTP, ограниченные повторы только временных ошибок, backoff и jitter, уважать Retry-After. 401/403 — проверить авторизацию/доступ; 402/429 — различать квоту и throttling по контракту; 404 карточки — недоступность объекта; 5xx/сетевой сбой — деградация. Не повторять без конца, не обходить лимиты ротацией ключей. Показать состояние сервиса без раскрытия секретов.
- Лимиты внешних запросов глобально по приложению; внутренние лимиты на пользователя/поиск, длина запроса, число страниц; метрики cache hit/miss, вызовы API, HTTP-статусы, задержки, ошибки импорта. Не логировать лишние пользовательские поисковые данные.
- Проверить миграции, резервное копирование media вместе с БД, возможность удаления или замены постера и внешних метаданных без потери пользовательской записи. Не удалять глобальную карточку при удалении фильма из библиотеки одного пользователя.
- До публичного запуска подтвердить условия доступа, права на сохранение/публичное отображение метаданных, описаний и постеров, срок хранения и атрибуцию. Успешный API-ответ не предоставляет автоматически лицензию на изображения. В доступной документации не удалось подтвердить разрешение на бессрочный локальный кеш и публичную раздачу. При отсутствии разрешения использовать только допустимые поля, сроки и способы показа; заглушки/ссылки там, где требуется. Не копировать отзывы, видео и галереи. Сохранять возрастную маркировку как метаданные, не использовать каталог для обхода возрастных ограничений.

## 7. Приёмочные тесты

Автоматические тесты с моками/fixtures, без платных внешних запросов в CI. Отдельный ручной smoke-тест на новом ключе и целевом хосте.

1. Поиск ранее неизвестного произведения: один внешний поиск, результаты видны, нет загрузки всех staff и постеров.
2. Повтор того же поиска двумя пользователями при актуальном кеше: 0 внешних запросов; выдача корректно объединена, учитывает страницу и фильтры.
3. Локальное совпадение не скрывает другое одноимённое произведение; выбор по ID, не по названию.
4. Импорт нового ID: 2 запроса метаданных, один постер при разрешении; карточка и связь с пользователем созданы.
5. Повторное/одновременное добавление: одна общая карточка, уникальные пользовательские записи, нет дублирования ID и импортов. Проверить с настоящим PostgreSQL и конкурентными транзакциями.
6. Фильм, сериал, аниме: корректные годы, несколько режиссёров, nullable-поля, жанр «аниме», постер на другом языке. Использовать три тестовых ID выше для smoke-теста; для CI создавать минимальные синтетические fixtures без копирования чужих описаний/изображений.
7. Отсутствующие русский вариант имени и название, неизвестный тип, пустой или недоступный staff, отсутствующий/битый постер: UI и импорт работают предсказуемо, ошибки не скрываются.
8. 401/403/402/429/5xx/timeout: ограниченные запросы, сохранённый каталог доступен, ошибочный ответ не становится кешированным пустым поиском. Проверить истечение TTL и обновление без потери личных данных.
9. Безопасность: ключ не попадает в браузер, логи и загрузчик изображений; чужие личные записи недоступны; нельзя подставить произвольный URL или обойти права; размер файла ограничен.
10. Подтвердить, что открытие библиотеки, повторное добавление уже импортированного произведения и сохранение оценки не вызывают API.
11. Проверить права хранения/отображения материалов и поведение при отключённом локальном сохранении постеров.

## 8. Задание основному агенту
