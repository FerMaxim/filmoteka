25 ноября 2026 владелец выбрал Kinopoisk API Unofficial вместо TMDB, общий локальный каталог, поиск с кешированием и импорт выбранного произведения по требованию (R36). Эти решения приняты. По R37 также согласованы TTL 24 ч / 10 мин / 30 дней, ограниченное ручное обновление и показ оригинального названия/имени, если русского нет. **Исторически интеграция была отложена владельцем до R47.** Действующий объём ограничен разделом R47 и задачей T-008. Стек Django/PostgreSQL, разделение ролей, система оценивания и утверждённый дизайн сохраняются.

Основание: [отчёт владельца от 24 ноября](ASSETS/CATALOG/Filmoteka_Kinopoisk_Integration.md). Это внешний входной материал: описанные в нём модели/маршруты/TTL являются предложениями, а пункт «реализовать» не заменяет текущее поручение только спроектировать. Исходные info.json/TXT/JPEG, кабинет и ключ владельца не предоставлены этому ревью; тесты трёх произведений известны из отчёта, независимо не повторены.

## Первый выпуск · R47

Этот раздел задаёт текущий объём [T-008](TASKS/T-008.md) и заменяет прежние предложения об автоматическом поиске при наборе, выдаче v2.1, обязательных details/staff и хранении расширенных метаданных. Ниже сохранён исходный проект для контекста. В T-005 уже есть accounts, Work, Entry и приватный локальный поиск.

- Локальные совпадения показываются сразу после отправки запроса, внешняя выдача дополняет их. Использовать один GET `/api/v2.2/films?keyword=…&page=…`. По [OpenAPI](https://kinopoiskapiunofficial.tech/documentation/api/openapi.json) он возвращает items с kinopoiskId, nameRu, year, ratingKinopoisk, ratingImdb и ссылками на постер. Баллы nullable. Предыдущий v2.1 возвращает один rating и не подходит для этой выдачи. Объединять карточки с одинаковым внешним ID, сохранять разные одноимённые работы. Следующая страница только по действию пользователя.
- Один основной постер на произведение. В выдаче лениво показывать разрешённый preview основного постера. Сервер не скачивает файлы результатов заранее. При добавлении разрешён максимум один сохранённый основной постер, если подтверждены права. При отсутствии прав на показ или отсутствии изображения — заглушка. Галереи, актёрский состав, описание и альтернативные изображения вне первого выпуска.
- Сохранять при явном добавлении выбранного ID из серверного кеша (ID и отображаемое название обязательны, год, два рейтинга и постер допускают пропуск). Это импорт по требованию без повторного API-вызова. Если данные выбранного результата более недоступны в кеше и работы ещё нет, допустим один GET `/api/v2.2/films/{id}` под общим бюджетом. При наличии локальной работы новая личная запись использует её. Повторное чтение карточки и добавление из каталога используют 0 вызовов.
- Холодная страница поиска — 1 JSON-запрос, свежий общий кеш — 0, добавление из свежей выдачи — 0. Общий ключ кеша включает нормализованный запрос и страницу. TTL по R37: 24 ч для результатов, 10 минут для успешной пустой выдачи, 30 дней свежести карточки. Истечение свежести не запускает фоновую загрузку. Ручное обновление ограничено общим бюджетом. Количество обращений к изображениям измерять отдельно. До живой проверки неизвестно, учитывает ли их кабинет в суточной квоте.
- По кабинету владельца: бесплатный тариф, 500 запросов в день, ключ есть. До проверки границы суток использовать настраиваемый общий лимит с запасом, предлагаемый старт — до 450 API-попыток в скользящие 24 часа на ключ. Резервировать бюджет до вызова атомарно на стороне сервера, считать ошибки и повторы. При 402/429 и исчерпании бюджета прекратить новые обращения согласно квоте или паузе. Показывать локальные данные и допустимый кеш, сообщать о временной недоступности внешней выдачи. Запросы к API выполняет сервер только после проверки сессии.
- До живого включения подтвердить условия хранения и показа данных, атрибуцию, режим постеров и учёт запросов. Тесты на fixtures можно выполнять сразу. Продажа тарифа или расходы не входят в задачу.

## Что есть в коде и как это соотносится с архитектурой

Проверена база проектирования `ff6f14c` (ветка T-004 поверх T-003). В filmoteka есть настройки, health, Django-оболочка главной и /prototype/; произведения, поиск и личные действия пока в JS-памяти. Моделей work/entry/rating, приложений accounts/catalog/collection, серверного поиска, кеша и адаптера TMDB нет. Они описаны как будущие границы в ARCHITECTURE. Зависимости: Django, psycopg, WhiteNoise; HTTP-клиент и обработка изображений пока не выбраны. Следовательно, это создание доменных модулей, не миграция действующего TMDB-клиента и не перенос пользовательских данных из демо.

Согласованная архитектура уже разделяет work, external_ref и личную entry, допускает импорт через адаптер/management command и уникальность внешнего ID. Новый контракт добавляет внешний поиск, общий кеш и импорт по запросу пользователя; management command остаётся для ограниченного обновления, а не единственным способом получить карточку. catalog не зависит от collection: HTTP-операция добавления вызывает сервис catalog, затем операцию collection от текущего пользователя.

## Предлагаемые модели и миграции

Имена логические, уточняются при создании приложений; не создавать параллельные ExternalWorkId/LibraryEntry рядом с уже согласованными external_ref/entry.

| Сущность | Предлагаемые изменения |
|---|---|
| work | Общая карточка без owner. Непустой display title, nullable name_ru/name_original/name_en, year/start_year/end_year, source_type, внутренний kind, is_serial и отдельный признак is_anime; nullable описания/страны/жанры/длительность/возраст; внешние рейтинги и голоса отдельно от личного rating. Источник неизвестного типа сохранять, не придумывать классификацию |
| external_ref | FK work, provider=`kinopoisk_unofficial`, external_id строкой, UNIQUE(provider, external_id). IMDb ID — отдельная ссылка provider=`imdb` при наличии; конфликт ID не объединять автоматически. source_last_sync, fetched_at, last_success_at, details_status/staff_status и срок свежести по источнику; ошибка обновления отдельно от последнего успеха |
| person / credit | person: provider/external_person_id UNIQUE, русское и исходное имя nullable. credit: work/person/profession_key/порядок; уникальность роли в работе, несколько режиссёров и ролей одной персоны; DIRECTOR отдельно от дубляжа. Не загружать карточку каждой персоны дополнительным запросом |
| poster_asset | Один активный основной posterUrl на work, путь Storage либо разрешённая ссылка, URL/источник, MIME/формат, ширина/высота, статус и timestamps. Один-к-одному с work для MVP; бинарных изображений в БД нет. ready/missing/failed/disabled различимы |
| catalog_search_cache | Общий provider + версия нормализации + normalized_query + page + канонический ключ filters; UNIQUE по ключу. Компактный JSONB кандидатов, provider pagination, fetched_at/expires_at; без личных данных. Хранить nullable недоступные поля, не превращать поисковую карточку в work |
| catalog_fetch_lease | Ключ операции search/import/refresh, token владельца, expires_at и fencing generation. Короткие атомарные захват/освобождение и проверки перед публикацией; общий для web-процессов, не process-local lock |
| Ограничитель провайдера | Общий счётчик/бюджет в PostgreSQL с короткой блокировкой строки и next_allowed_at/backoff_until; ограничивает все API-операции приложения, а не каждый web-worker отдельно |
| entry, rating, emotion, recommendation | Создать по существующему ARCHITECTURE, не менять формулу или поля оценки ради каталога. entry UNIQUE(owner, work); внешний рейтинг не записывается в rating. Глобальная work не удаляется при удалении личной entry |

Предложение хранения жанров/стран: нормализованные массивы значений JSONB на work в MVP, без отдельной модели ради отсутствующих пока фильтров. Для служебных состояний — проверяемые choices/ограничения, nullable числовые поля с допустимыми диапазонами; невозможные данные отклонять/помечать, не подменять нулём. Согласованный fallback (R37): при отсутствии русского названия/имени разрешён оригинальный вариант. Предлагаемый полный порядок display title: nameRu → nameOriginal → nameEn; при отсутствии всех импорт обязательных данных не завершать, показать ID и ошибку в выдаче. Неизвестный source_type: сохранять raw и техническое unknown; политику отображения согласовать (Q4).

Пакеты миграций: (1) каталог и внешние ID; (2) люди/роли и постер; (3) кеш/lease/ограничитель; (4) accounts и entry по прежнему плану, затем связь операций добавления. Порядок accounts/entry можно вынести перед (3), интеграционные сценарии требуют их наличия. Никаких миграций оценок для изменения формулы. Проверить пустую БД и обновление предыдущего SHA. Если к началу реализации появятся реальные модели/данные, заново сверить схему, выполнить только добавляющие миграции и план переноса; демо JS не мигрировать. pg_trgm/индекс добавлять только после замера, начальный локальный поиск — параметризованный ORM по нормализованным названиям и году.

## Контракт провайдера и проверенность

База HTTPS https://kinopoiskapiunofficial.tech, ключ только серверный заголовок X-API-KEY, Accept application/json. Не передавать ключ в URL, браузер или загрузчик постеров. KINOPOISK_API_KEY в окружении, .env.example с пустым значением; KINOPOISK_BASE_URL не позволяет пользователю подменить хост. Возможную ранее раскрытую учётную запись из отчёта не считать проверенной: перед живым smoke владелец обеспечивает действующий нераскрытый ключ; ключ в задачу/КБ не вставлять.

Предложение MVP: один GET /api/v2.1/films/search-by-keyword с keyword/page. Нормализовать films/filmId/pagesCount в свой SearchCandidate DTO; полная карточка GET /api/v2.2/films/{id} — другой DTO; staff GET /api/v1/staff с filmId. Альтернативный /api/v2.2/films не вызывать параллельно «на всякий случай». В текущей OpenAPI у выбранного поиска нет фильтров жанра/типа/года; UI не должен обещать полноту таких внешних фильтров. Их добавление потребует выбора v2.2 с соответствующим контрактом либо явного ограничения локальными результатами.

25 ноября 2026 прочитана [OpenAPI поставщика](https://kinopoiskapiunofficial.tech/documentation/api/openapi.json): указанные методы присутствуют, у v2.1 страница до 20 результатов, page в диапазоне 1–20. Общий лимит описан как 25 запросов/с на пользователя поставщика; один ключ приложения не означает по 25 на каждого пользователя Filmoteka. 402 обозначает исчерпание общей/дневной квоты, 429 — ограничение частоты. Фактический тариф, доступность production и права на хранение этим не подтверждены. [Тарифы](https://kinopoiskapiunofficial.tech/rates) в текстовом web-доступе показали только требование JavaScript. Живых поисков/staff/details и расходов квоты в этой сессии не было. Перед реализацией повторно сверить текущую схему и выполнить контролируемый smoke отдельно от CI.

Маппинг: nameRu/nameOriginal/nameEn → названия; year/startYear/endYear → отдельные годы; type/serial → формат, genres → жанры и is_anime; filmLength/ratingAgeLimits nullable; ratingKinopoisk/ratingImdb и voteCount только внешние показатели. lastSync — время источника, не fetched_at. staffId/nameRu/nameEn/professionKey → персона и роль; не ограничивать одним режиссёром, не придумывать перевод. Только posterUrl; coverUrl, logoUrl, галереи, видео, отзывы и сезоны вне MVP. Основной постер может иметь иностранные надписи. Отчётный «аниме» как жанр не заменяет формат фильма/сериала.

## Поиск и пользовательские сценарии

Предлагаемое поведение (сохраняет личные сценарии U01–U09):

1. При добавлении пользователь вводит название. UI обращается только к Django; минимум 3 символа, debounce 600 мс и Enter — стартовые предложения, не утверждённые ограничения. Ограничить длину запроса и страницы, отменять/игнорировать устаревшие ответы по sequence ID. Возврат к вводу не должен менять выбранное произведение или форму оценки.
2. Django нормализует Unicode (NFKC), регистр, пробелы; ё/е — только поисковый ключ, не отображаемые данные. Исходный ввод остаётся в UI; поставщику передаётся строка через params HTTP-клиента. Общий кеш по нормализованному ключу не содержит ID пользователя. При влиянии нормализации на результат её версионировать; внешняя лексика/транслитерация проверяется smoke.
3. Отдельно получить локальные совпадения и страницу внешних кандидатов: локальная выдача имеет собственную пагинацию, внешняя — свою page/has_more. Дедупликация по external_ref, никогда по названию/году. DTO результата различает work_id и ещё не импортированный provider/id, тип результата, свежесть и полноту. Нет «общего точного total» из суммы двух источников.
4. При свежем кешe — 0 внешних поисков. При cache miss — один запрос страницы под общей lease. Локальный матч не отменяет внешний поиск на miss: иначе исчезают одноимённые произведения. Предлагаемый default — автоматический поиск при miss, отдельно можно запросить режим «только локально»; итог UX согласовать Q1. Кандидатов кешировать компактно, staff/details для всей страницы не вызывать. Внешний preview показывать лишь разрешённым способом; до подтверждения прав — заглушка, без скачивания всех постеров.
5. Явное добавление выбранного внешнего ID вызывает импорт только этого ID; затем owner-only операция создаёт entry. Обычное чтение локальной карточки/библиотеки/профиля, сохранение оценки и повторное добавление готовой work не обращаются к провайдеру. Проверять полномочия до внешних затрат. В MVP предлагается запуск внешнего поиска/импорта только вошедшим пользователем; гостевой просмотр локальных данных не расширяет прежние права и остаётся закрыт до отдельного решения.
6. При ошибке показать локальные и допустимые устаревшие результаты с отметкой неполноты и возможностью повторить. «Ничего не найдено» допустимо только для успешной пустой выдачи, не для timeout/квоты. При импорте — состояние ожидания, готово, неполные данные либо понятный отказ; повторный click не дублирует запись. При недоступном постере — заглушка, при отсутствии русского имени — согласованный fallback. Поля из внешнего источника всегда экранировать.

Проект HTTP в рамках существующей архитектуры: GET /catalog/?q=&page= читает/кеширует кандидатов без создания work/entry, GET /works/{id}/ читает только локальную work. POST /catalog/imports/ с provider/id запускает явный импорт; POST /me/library/add/ импортирует при необходимости и идемпотентно добавляет владельцу entry; POST /me/works/{id}/library/ остаётся для флагов существующего внутреннего ID. Это предложенные маршруты, не реализованные. Вход не принимает URL поставщика или owner. Синхронный успех POST → 303 на локальную страницу; ошибка формы → 422; чужой объект/версия — существующие правила 403/404/409. Если другая операция уже держит lease, короткое ожидание или 202 с локальным operation token и ограниченным polling (HTML fallback ожидания), не длительная SQL-транзакция. Конкретный формат partial/pending ответа согласовать до кода.

## Импорт, кеш и конкурентность

Сначала перечитать external_ref. Готовую work использовать без API даже при прошедшем TTL; устаревание само по себе не запускает обновление при добавлении. Для нового ID взять lease, повторно проверить запись, затем details и staff вне SQL-транзакции. Минимум для публикации work: валидный ID, совпадающий с выбранным, и пригодное название; неподдерживаемые/невалидные поля не выдумывать. Ошибка details не создаёт entry. Предложение: staff/poster необязательны, при их сбое work/entry можно создать как partial, отдельно last_error и status; успешный пустой staff отличается от network failure. Последующее обогащение — явный retry/команда, не каждый просмотр.

В короткой atomic-транзакции проверить действительность token/generation lease, создать/обновить work и external_ref под UNIQUE, людей/credit, синхронизационные статусы; затем отдельная операция collection создает entry с UNIQUE(owner,work). При конфликте переиспользовать победившую work, не оставлять лишнюю глобальную карточку. Если личное добавление не удалось после публикации каталога, глобальная work может остаться: повтор безопасно использует её. Не обещать общую атомарность HTTP, Storage и БД. Удаление личной записи не удаляет work или постер других пользователей.

Lease имеют срок и owner token: освобождает только владелец, просроченный процесс не публикует данные. HTTP timeout/число попыток ограничены, lease покрывает бюджет работы; ожидание с конечным сроком. После сбоя процесса lease истечёт. Одновременные нормальные cache miss/import объединяются, но ровно один внешний вызов при любых crash/неопределённом timeout гарантировать нельзя; повтор после аварии допустим, дубли в БД — нет. Это проверять отдельно, не выдавать UNIQUE за дедупликацию внешних запросов.

Согласованные владельцем стартовые настройки (R37): TTL поиска 24 ч, успешного пустого ответа 10 мин, свежести карточки 30 дней; обновление ограниченной ручной командой, без обязательного планировщика. TTL конфигурируемые и не являются квотой поставщика. Ошибка API не записывается как пустой success; можно отдельно задать короткий backoff/circuit state без подмены кеша. Очистка кеша — ограниченная management command. Устаревшие карточки не удаляются; refresh — явная команда/операция с квотой, сохраняющая last_success и пользовательские ссылки. Успешный пустой новый staff может заменить прежний список; ошибка не стирает его. Не затирать поля отсутствующим ключом/ошибочным частичным ответом; nullable null из успешного полного ответа отличать от отсутствующего поля.

Ожидаемый расход в штатном случае: новый поиск страницы — 1 API-вызов, новый импорт — 2 (details+staff), плюс отдельный poster HTTP при разрешении. Кеш hit и готовая work — 0. Страницы/ретраи/refresh считаются отдельно; новый запрос текста может потребовать API даже при локальной нужной карточке. Учёт CDN в квоте проверить, не обещать 3 в каждом случае.

## Постер, безопасность и эксплуатация

Один основной posterUrl; в UI сохранить геометрию утверждённых карточек, применять object-fit:cover к изображению близкому к 2:3 без растягивания. Не менять внешнюю пропорцию карточки Свет 04+ ради неодинаковых размеров файлов. Во время проектирования/до подтверждения условий policy=placeholder; local copy или remote URL разрешать только после решения по правам. Ссылка/hotlink тоже не считается автоматически разрешённой. Недоступный постер не блокирует личное добавление.

Для будущего local-copy: HTTPS, разрешённые хосты API отдельно от CDN, запрет credentials/нестандартных схем/внутренних IP, проверка DNS и каждого редиректа, streaming с лимитом байт/пикселей/времени, MIME + декодирование, безопасный растровый результат без метаданных, обоснованный декодер (например Pillow, пока не добавлен). API-ключ не передавать CDN, абсолютные URL клиента не принимать. Источник URL и редирект проверять и на SSRF, даже если URL получен из API. Конкретный allowlist получить из smoke/документации, не разрешать все хосты.

Django Storage с неизменяемым уникальным именем файла (в логическом пространстве catalog/kinopoisk/id), staging/проверка до публикации; БД переключает ссылку только на полностью готовый объект. Storage может не поддерживать атомарный rename: не полагаться на локальный os.rename как универсальный контракт. При rollback/конкурентном проигрыше убрать только свой временный объект, периодически собирать сироты. Старый рабочий постер сохранять до успешного переключения, не удалять общий файл до проверки ссылок.

Глобальный бюджет запросов по ключу приложения плюс внутренние лимиты пользователя/поиска. Числа тарифа, время ожидания, максимум страниц и файлов не выдумывать. 401/403 не ретраить как временный сетевой сбой; 402 — квота, 429 — backoff с Retry-After при наличии, 5xx/timeout — ограниченный retry с jitter и общим deadline. Логи не содержат ключ, cookie, оценки, комментарии, полные тексты запросов; метрики cache hit/miss, число API-вызовов, коды, latency и partial failures без персональных payload. Нельзя обходить квоту ротацией ключей.

БД и media резервируются согласованно; проверка восстановления пары и уборка временных файлов относятся к будущей эксплуатации. Отзыв/замена внешних метаданных или постера по условиям источника не удаляет личные оценки/entry; допустимый технический tombstone сохраняет внутренний PK и ссылки, подробности по правам согласовать. Нового сервера, Redis, Celery, очереди и расписания сейчас не создаётся. Нативный процесс Django/PostgreSQL и ограничения ENGINEERING неизменны.
