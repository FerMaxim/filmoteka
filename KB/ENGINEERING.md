# Инженерный регламент

## Рабочий цикл и передача

- Разработчик (Sol) реализует утверждённые этапы, проверяет, исправляет, оформляет локальные коммиты и передаёт по [WORKFLOW](WORKFLOW.md). Обратимые детали решает по контракту и записывает существенные допущения. Использует штатные операции модулей и существующие компоненты.
- Ревьюер в отдельном чате независимо проверяет diff от main, код, контракты и тесты. Небольшие инженерные исправления указывает в отчёте. Публикация, PR, CI и merge закреплены за ревьюером.
- Эксплуатация в третьем чате готовит сервер и выкладывает проверенный SHA main по [OPERATIONS](OPERATIONS.md). Ошибки кода передаёт разработчику, версионируемую конфигурацию ревьюеру. Назначение в BACKLOG не меняет полномочия.
- Продукт, видимость, утверждённый дизайн, архитектурные границы, расходы и необратимые миграции требуют решения владельца. До решения выполнять проектирование и независимые работы. Обосновывать новые зависимости и обходы границ задачей и стоимостью сопровождения.

## Выбор стратегии в Codex

Сначала используй штатную команду, если результат проверяется однозначно. Веди связную работу сам. Делегируй независимое исследование, когда оно даёт выигрыш по времени, объёму контекста или глубине анализа и текущий клиент допускает запуск. Обычная постановка — ID, результат, критерии и границы. Выбор помощника и уровня reasoning принимает ведущий. Если клиент требует явное поручение на запуск, применяй его правила. Смену модели ведущего задаёт владелец в клиенте.

Начинай с GPT-6.2 Sol Medium для разработки, повышай до High при сложной реализации. Для короткого исследования используй GPT-6 Luna High, для сложного анализа рисков — GPT-6.2 Astra Medium с повышением до High по необходимости. GPT-6.1 Terra Medium — кандидат для отдельного визуального пилота. Сверяй пары с доступными моделями и уровнями в текущем клиенте. Если нужная пара недоступна, используй настройки ведущего либо выполни исследование сам.

До повторной оценки P4 запускай не более одного помощника одновременно, без вложенного делегирования и только для чтения. Бриф содержит цель, SHA, разрешённые источники, границы и формат ответа. Передавай минимум контекста, исключай секреты и приватные данные. Ведущий сверяет выводы и отвечает за результат. Официальное ревью ведёт отдельный ревьюер. После двух неудач по одной причине меняй стратегию или фиксируй блокер.

При передаче запиши в карточке класс и риск, запрошенную и подтверждённую модель и reasoning, число запусков, итог первой передачи, число переделок, время до приёмки, вмешательства владельца и расход по доступному счётчику. Если данных ещё нет, дополни запись при приёмке или отметь недоступность счётчика. Сравнивай задачи одного класса и риска с самостоятельной работой по времени, переделкам и измеренному расходу. [Пилот и ограничения](TASKS/T-009.md#p4--пилот-делегирования).

## GitHub и выпуск

Устойчивая main, Conventional Commits для коммитов и squash. Интеграция через PR, предпочтительно squash. Запрещены force push, удаление main и переписывание опубликованной истории. При конфликте опубликованной ветки влить main и повторить затронутые проверки.

Ревьюер вправе публиковать ветки и создавать PR в `FerMaxim/filmoteka` после локального ревью и проверки секретов/приватных данных. Заполнить [шаблон PR](../.github/pull_request_template.md). Существенные исправления возвращать разработчику. Для merge нужны разрешение владельца на PR или объём слияний, выполненные критерии, закрытые замечания и успешный `quality-gate` текущего head. Новый head требует повторной проверки. Отсутствие, отмена или провал обязательной проверки блокируют merge. Настроить обязательный PR и quality-gate без обхода, где позволяют права и тариф. Проверить правила пробным PR. При ограничениях применять процесс вручную и сообщить владельцу.

Поддерживать `CHANGELOG.md` / Unreleased. При выпуске — версия и дата, SemVer-тег `vMAJOR.MINOR.PATCH` на проверенном main. Исправления повышают PATCH, совместимые возможности MINOR, несовместимость стабильного контракта MAJOR. Первый номер определяется готовностью релиза.

## Минимально достаточные проверки

Использовать `python tools/check.py <набор>`. Набор выбирается по риску, без квот тестов и покрытия. Для значимой ошибки логики или безопасности нужен регрессионный тест.

| Набор | Применение |
|---|---|
| `target <pytest-node-id>` | Проверка изменённого сценария в разработке. |
| `quick` | Ruff, Django check, незаписанные миграции и quick-тесты с dummy backend. История PostgreSQL проверяется в full. |
| `full` | Quick-проверки кода, история миграций, миграции с нуля и старой схемы, вся коллекция pytest один раз, HTTP smoke и Playwright. |
| `smoke` | Django на loopback и одноразовой БД, таймаут readiness и HTTP live/ready. |
| `browser` | Playwright на изолированном экземпляре, визуальная приёмка по [DESIGN](DESIGN.md). |
| `docs` | Реестр, спецификации, ссылки, якоря и ID решений. |

Перед PR quick и проверки затронутого риска. Для документального diff достаточно docs, чистый CSS требует браузера и имеющихся проверок стилей. Перед merge — назначенные CI проверки; запросы с доступом, БД и формами требуют интеграции. Перед релизом full.

Формула — пустые критерии, ноль, крайние и частичные наборы, половина при округлении. Запись, доступ и импорт — HTTP/PostgreSQL, чужой объект, лишние поля, ограничения, откат, два соединения для гонок. Основные пути — Playwright на синтетических данных, оценка с перечитыванием, рекомендация и профиль в отдельных сессиях с согласованными правами.

Отчёт содержит команду, длительность, exit code и фактические числа passed/skipped/failed. На успехе сводка, на сбое имя проверки и релевантные строки; возвращать исходный ненулевой код. CI хранит артефакт команд, кодов и длительностей семь дней без окружения и дочернего вывода. Детали — в Actions. Результат применим при тех же входах, включая настройки и зависимости. Успешные полные логи агенту не нужны.

## Изоляция и миграции

Каждый прогон с БД создаёт одноразовый PostgreSQL 17 на `127.0.0.1`, временный каталог, отдельный порт, случайный пароль, роль и БД. Удалять из окружения рабочий `DATABASE_URL`, пароли и драйверные переменные переопределения адреса. До подключения сверять test settings, точные host/port, БД и роль. На служебном и каждом новом соединении до SQL приложения проверять `current_database()`, `current_user` и маркер кластера. Несовпадение завершает операцию. Регрессии проверяют запрет неверного адреса до подключения и неверного маркера до изменения схемы.

Штатные миграции подготавливают БД один раз. pytest-django использует совпадающий `TEST.NAME` и стандартную изоляцию. Защита действует для истории, миграций, pytest и тестового Django. Fixtures синтетические, внешние API подменены. Завершать только собственные процессы и удалять только временное хранилище прогона. Постоянная dev-база переживает restart.

Миграции хранить рядом с моделями. Проверять чистую и предыдущую схему. Предпочитать совместимое добавление, перенос, переключение чтения и отдельную очистку. Разрушительная миграция требует явного решения, копии, восстановления на отдельной БД и плана совместимого возврата.

## Безопасность

ORM или параметры SQL. Сортировки и изменяемые поля по allowlist. На сервере валидировать тип, длину, диапазон и принадлежность. Owner брать из сессии и ограничивать queryset. Проверять гостя, владельца и другого пользователя. Клиентский итог балла запрещён. Выдавать только поля, разрешённые [PRODUCT](PRODUCT.md).

Стандартные Django auth, hashers, валидаторы и ротация сессии. Изменение с cookie — CSRF middleware и token. Production — HTTPS, Secure cookies, HttpOnly для сессии, SameSite, ALLOWED_HOSTS, DEBUG=False. Пользовательский ввод экранировать, в DOM вставлять как текст. Ограничивать размер запроса, пагинацию и дорогие операции/вход через доверенный ingress с 429. Forwarded-заголовки принимать только от доверенного прокси. Правила пользовательских изображений — в [ARCHITECTURE](ARCHITECTURE.md#фотография-фона).

Секреты в окружении, `.env` вне Git. Не логировать ключи, cookie и личные комментарии. При утечке отзывать секрет. Фиксировать зависимости и Actions, проверять обновления CI и известными уязвимостями.

## Локальный запуск и CI

Нативные Django и PostgreSQL без Docker/Compose в разработке, CI и эксплуатации. [PowerShell](LOCAL_DEVELOPMENT.md) описывает локальную среду. Тестовый Django получает loopback-порт через привязку сокета. PostgreSQL из `PG_BIN` или `PATH`.

Actions запускается всегда для PR и вручную. Linux, Python 3.13, uv, PostgreSQL 17. Ключ кеша учитывает ОС, архитектуру, Python и lock. Permissions `contents: read`, сторонние Actions по SHA, concurrency по PR с отменой прежнего прогона. Целевые лимиты 10 мин для quick и 25 мин для integration/browser уточняются по замерам. Только известные пути документации дают docs. Неизвестный путь, пустой или недоступный diff и ручной запуск требуют full. Quality-gate запускается и после сбоя зависимости и успешен только при успехе назначенного набора.
