# Инженерный регламент

## Рабочий цикл и передача

Агент-разработчик (Sol) реализует утверждённые этапы, выполняет локальные проверки, исправляет замечания, сопровождает код и оформляет локальные коммиты. Публикация, создание PR и merge закреплены за отдельным агентом-ревьюером в другом чате Codex. Третий агент эксплуатации отвечает за сервер и выкладку по [OPERATIONS](OPERATIONS.md); права интеграции остаются у ревьюера.

| Ситуация | Полномочия Sol |
|---|---|
| Локальная реализация в рамках контрактов, тесты, обратимые исправления | Решить самостоятельно. Переиспользовать существующие операции и компоненты |
| Неопределённая техническая деталь с обратимым результатом | Выбрать минимальный вариант по существующему контракту, записать предположение при передаче |
| Изменение продукта, видимости, утверждённого дизайна, архитектурных границ, необратимые миграции или расходы | Подготовить варианты, влияние и рекомендацию. Получить решение владельца для затронутой части, параллельно делать независимые задачи |

Ревьюер самостоятельно сверяет diff относительно main, код, контракты и тесты. Небольшие инженерные исправления допустимы с указанием в отчёте. Порядок старта и передачи — в [WORKFLOW](WORKFLOW.md).

Чтобы сохранять границы, проводить изменения через штатные операции модуля, не дублировать серверные правила в шаблонах, сохранить один источник решения по доступу. Новую зависимость, новый сервис или межмодульный обход обосновать задачей и стоимостью сопровождения. Начинать с проверки diff и контрактного теста. Общий автоматический архитектурный контроль добавлять при наблюдаемом нарушении.


## GitHub и выпуск

Стабильная main. ID и имя ветки задачи определяет [WORKFLOW](WORKFLOW.md#старт-задачи). Коммиты и итоговый squash-заголовок по Conventional Commits, например feat(ratings): добавить быстрое оценивание. Не переписывать опубликованную историю, запретить force push и удаление main. Интеграция через PR, предпочтительно Squash and Merge. При конфликте с опубликованной веткой влить main в ветку и повторить затронутые проверки.

Шаблон PR хранится в [.github/pull_request_template.md](../.github/pull_request_template.md) и включает:

- Задача и критерии приёмки
- Изменения и влияние на поведение
- Фактические команды, результаты, пропуски и причины
- Обновления KB и CHANGELOG
- Миграции, откат и риски, если применимо
- Скриншоты значимых визуальных изменений

Владелец разрешил ревьюеру публиковать рабочие ветки и создавать PR в публичном `FerMaxim/filmoteka`. Перед push ревьюер завершает локальное ревью без блокирующих замечаний и проверяет публикуемые коммиты на секреты и приватные данные. После создания PR ревьюер следит за GitHub Actions, разбирает сбои, сверяет актуальность КБ, CHANGELOG и версий. Существенные исправления CI и реализации разработчик оформляет локальными коммитами и повторно передаёт ревьюеру.

Для merge ревьюер сверяет критерии, разрешение владельца на данный PR или ранее разрешённый объём слияний, отсутствие нерешённых замечаний и успешные обязательные проверки именно текущего head. При смене head проверить снова. Провал, отмена или отсутствие обязательного результата блокируют merge. На GitHub настроить обязательный PR, единый обязательный статус quality-gate и запрет обхода для main, где позволяют права и тариф. При ограниченном тарифе применять тот же регламент вручную и сообщить владельцу об отсутствии технического принуждения. GitHub Free поддерживает защиту для публичных репозиториев, для частных применимы Pro, Team и Enterprise. На этапе подключения проверить видимость, права, активные правила и пробный PR. [GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

Вести CHANGELOG.md с разделом Unreleased для пользовательских и значимых инженерных изменений. Перед согласованным выпуском перенести записи под версию и дату. SemVer vMAJOR.MINOR.PATCH для Git-тега на проверенном коммите main. Исправления повышают PATCH, совместимые возможности MINOR, несовместимый стабильный контракт MAJOR. Первый номер версии определить по фактической готовности релиза.

## Минимально достаточные проверки

Цель — уверенность в затронутом поведении. Не задавать процент покрытия или квоту тестов. Для существенного исправления бизнес-логики или безопасности добавить воспроизводимый регрессионный тест на самом дешёвом достоверном уровне. Не подгонять корректные ожидания под дефект.

| Риск | Проверка |
|---|---|
| Формула | Unit на отсутствие критериев, ноль, крайние и частичные наборы, согласованную границу округления |
| Записи, доступ, импорт | Интеграция через HTTP и PostgreSQL, чужой объект, лишние поля, ограничения, откат и две конкурентные записи через отдельные соединения |
| Основные пользовательские пути | Playwright на синтетических данных. Оценить и перечитать, порекомендовать и открыть профиль в отдельной сессии с согласованными правами |
| Запуск приложения | Smoke запускает Django на loopback с изолированной БД, ждёт readiness с таймаутом, проверяет liveness и доступные страницы. Readiness подтверждает подключение к БД |
| Интерфейс | Браузер на мобильной и широкой ширине. Проверить клавиатуру, фокус, контраст, reduced motion, отсутствие перекрытий, горизонтального скролла и JS-ошибок. Сохранить скриншоты для PR |

Один Python-диспетчер `tools/check.py` используется на машине разработчика и в GitHub Actions.

| Команда | Что выполняет |
|---|---|
| python tools/check.py target <pytest-node-id> | Один модуль или сценарий |
| python tools/check.py quick | Ruff lint/format check, Django check, отсутствие незаписанных миграций и pytest-сценарии с меткой quick. Django использует dummy backend, поэтому проверка истории миграций PostgreSQL здесь отсутствует |
| python tools/check.py full | Проверки кода и истории миграций, миграции с нуля на одноразовой PostgreSQL, вся коллекция pytest за один прогон, HTTP smoke и Playwright |
| python tools/check.py browser | Playwright против локального тестового экземпляра, снимки выбранных экранов при визуальных изменениях |
| python tools/check.py smoke | Запуск одноразовой PostgreSQL и Django, проверка `/health/live` и `/health/ready` через HTTP |
| python tools/check.py docs | Локальные ссылки и целостность изменённых инструкций |

В разработке запускать target. Перед PR quick и проверки затронутого риска. Для документации достаточно docs, для чистого CSS браузерная проверка и имеющиеся проверки стилей. Перед merge малый быстрый набор выполнять целиком в CI, изменения доступа, БД и форм требуют интеграционных проверок. Перед релизом обязателен full. Отчёт содержит команды, длительность, фактические количества прошедших, пропущенных и упавших тестов, код завершения. Для нетестовой команды указывать её результат. На успехе выводить сводку, на сбое — имя проверки и релевантный фрагмент. Возвращать исходный ненулевой код дочерней команды. CI хранит журнал команд, кодов и длительности как артефакт на семь дней. В артефакт не попадают окружение и вывод дочерних процессов. Детали тестов доступны в журнале задания Actions. Переиспользовать результат при идентичных входах, включая настройки и зависимости. Успешные логи не требуют ИИ-ревью.

## Изоляция и миграции

Для каждого тестового запуска с БД поднимать отдельный локальный кластер PostgreSQL 17 на `127.0.0.1` со своим временным каталогом данных, отдельным портом, случайным паролем, тестовой ролью и БД. Диспетчер передаёт дочерним процессам координаты только этого запуска. Рабочий `DATABASE_URL`, пароли и переменные драйвера, переопределяющие адрес, исключить из тестового окружения. До подключения проверять test settings, точный адрес и порт, имя БД и роли. На каждом новом соединении до SQL приложения сверять `current_database()`, `current_user` и маркер, заданный при инициализации кластера. Несовпадение завершает операцию с ошибкой. Регрессии проверяют отказ на неверном адресе до подключения и на неверном маркере до изменения схемы. Интеграции используют синтетические данные и заглушки внешних API.

Запуск создаёт тестовую БД один раз. Диспетчер применяет штатные миграции. Фикстура pytest-django подключается к готовой БД с совпадающим `TEST.NAME`, а тесты используют изоляцию Django. Защита соединений распространяется на проверку истории, миграции, pytest и тестовый Django. При остановке или сбое диспетчер завершает только созданные им процессы и удаляет только временное хранилище своего запуска. Постоянная dev-база сохраняется при остановке приложения и штатном перезапуске PostgreSQL.

Миграции версионируются рядом с моделями. Проверять чистую установку и переход с предыдущей схемы. Предпочитать добавление совместимого поля, перенос данных, переключение чтения, затем отдельную очистку. До разрушительной миграции — явное согласование, резервная копия, проверенное восстановление на отдельной БД и план возврата приложения к совместимой схеме.

## Безопасность

ORM и параметры для SQL, сортировки и изменяемые поля по разрешённому списку. На сервере проверять диапазоны, длины, типы и принадлежность объекта, брать owner из сессии. Приватные запросы ограничивать владельцем прямо в queryset. Профиль выдаёт только разрешённые поля. Проверять матрицу гость / владелец / другой пользователь. Итоговый балл от клиента не принимать.

Использовать стандартные Django authentication, password hashers, валидаторы и ротацию сессии. Для всех изменяющих запросов с cookie обязательны CSRF middleware и token, в production HTTPS, secure cookies, HttpOnly для сессии, SameSite, ALLOWED_HOSTS, DEBUG=False. Экранировать пользовательский текст средствами шаблонов, вставлять в DOM как текст. Ограничивать размер запросов, пагинацию, частоту входов и дорогих запросов на доверенном ingress, с ответом 429. Не доверять произвольным forwarded-заголовкам. До включения загрузок определить допустимые типы, проверять содержимое и размеры, перекодировать изображения и выдавать со случайными именами из изолированного хранилища.

Секреты передаются через окружение, `.env` исключён из Git. Не логировать cookie, ключи и личные комментарии. Для будущей рабочей среды роль приложения имеет только необходимые права, DDL выполняет роль миграций. Зависимости и Actions фиксируются, обновления проходят CI и проверку известных уязвимостей. Утечка требует отзыва ключа. Внешние вызовы ограничены правилами [архитектуры](ARCHITECTURE.md).

## Локальный запуск и CI

Для разработки на Windows 11 нужны PowerShell, `uv`, Python 3.13 и нативная PostgreSQL 17. Зависимости устанавливаются из `uv.lock` командой `uv sync --locked`. Инструкция запуска перечисляет бинарные файлы PostgreSQL, которые нужны проверкам, и показывает, как проверить их доступность. Установленная PostgreSQL, dev-база и локальные настройки остаются на машине разработчика.

Для dev создать постоянную локальную БД, передать настройки окружения по шаблону `.env.example`, применить штатные миграции и запустить Django на `127.0.0.1:8000`. Шаблон содержит имена переменных и безопасные локальные примеры. Конкретные команды настройки и запуска описать в проверяемой инструкции PowerShell. Playwright использует собственную закреплённую версию браузера для `browser` и `full`. Для обычного запуска Django и `quick` браузер не требуется.

Actions на pull_request и по ручному запуску. Linux runner готовит Python 3.13, `uv` и PostgreSQL 17 и вызывает тот же диспетчер, что и локальная среда. Кэш пакетов привязан к ОС, архитектуре runner, версии Python и lock-файлу. Минимальные permissions `contents: read`, сторонние Actions закреплены по SHA. Для PR concurrency по номеру PR с `cancel-in-progress`. Плановые лимиты 10 минут quick и 25 минут integration/browser, уточнить по замерам. Классификатор путей работает внутри всегда запускаемого workflow. Только известные пути документации допускают `docs`, остальные изменения и ручной запуск требуют `full`. Итоговый `quality-gate` запускается и после ошибки зависимости, а его успех требует успешного результата назначенных проверок.

Среда разработки и проверок должна работать без Docker и без площадки для выкладки. Диспетчер находит бинарники PostgreSQL по `PG_BIN` или `PATH`. Перед созданием тестовой БД он проверяет идентичность служебного соединения с одноразовым кластером. Тестовый Django получает свободный HTTP-порт при привязке сокета и передаёт его диспетчеру. Для запуска разработки использовать [инструкцию PowerShell](LOCAL_DEVELOPMENT.md). Задачи выбора площадки, доставки и проверки развёрнутого экземпляра относятся к будущему этапу эксплуатации.

## Эксплуатация рабочей среды

Этот раздел применяется агентом эксплуатации после определения среды и полномочий владельца. Разработка, CI и сервер работают без Docker и Compose. Порядок передачи SHA, настройки, деплоя, проверки и отката — в [OPERATIONS](OPERATIONS.md).

- **Среды и доступ.** Рабочие секреты и данные отделены от разработки и CI. Приложение доступно через HTTPS. PostgreSQL и процесс Django работают в закрытой сети. Проверить production settings командой Django check --deploy. Административные операции выполняются с отдельными полномочиями. До запуска проверить сценарий доступа к аккаунту и восстановления доступа, применимый к согласованной регистрации. [Django deployment checklist](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/)
- **Резервирование.** Исходный вариант — ежедневная автоматическая зашифрованная копия PostgreSQL во внешнее хранилище. Защита нужна также для невоспроизводимых файлов, если они появятся, и для доступа к конфигурации восстановления через защищённый канал. Следить за возрастом последней успешной копии. До запуска восстановить копию в чистой изолированной среде и проверить вход и чтение контрольных записей. Повторять учение после существенного изменения схемы или механизма копирования. Периодичность и хранение согласовать с допустимой потерей данных и сроком восстановления. Базовая схема с суточным интервалом допускает потерю изменений между копиями. [Документация PostgreSQL](https://www.postgresql.org/docs/17/backup.html)
- **Обновления.** Выпускать проверенную версию с фиксированным идентификатором. Согласовать короткое окно обслуживания при несовместимой миграции. Проверить свежую копию, применить миграции, запустить новую версию и smoke через HTTPS. При сбое вернуть предыдущую версию, если схема совместима. Для несовместимой схемы использовать заранее проверенный план миграции вперёд или восстановления. Учитывать потерю записей после точки восстановления.
- **Наблюдаемость.** Настроить внешнюю проверку доступности и уведомления о недоступности, всплеске ошибок, нехватке места и просроченной копии. Хранить ограниченные по объёму журналы без секретов и пользовательского текста. Назначить получателя уведомлений. Проверить доступ к конфигурации, предыдущей версии и внешним копиям при потере основного хоста.
