# Инженерный регламент

## Рабочий цикл и передача

Агент-разработчик (Sol) реализует утверждённые этапы, выполняет локальные проверки, исправляет замечания, сопровождает код и оформляет локальные коммиты. Публикация, создание PR и merge закреплены за отдельным агентом-ревьюером в другом чате Codex. В новой сессии оба агента читают CURRENT_STATE, критерий этапа и нужные профильные разделы. Ищут конкретный маршрут или символ через rg. Пропускают .git, .venv, node_modules, vendor, build, dist, кэши, отчёты и бинарные ресурсы.

| Ситуация | Полномочия Sol |
|---|---|
| Локальная реализация в рамках контрактов, тесты, обратимые исправления | Решить самостоятельно. Переиспользовать существующие операции и компоненты |
| Неопределённая техническая деталь с обратимым результатом | Выбрать минимальный вариант по существующему контракту, записать предположение при передаче |
| Изменение продукта, видимости, утверждённого дизайна, архитектурных границ, необратимые миграции или расходы | Подготовить варианты, влияние и рекомендацию. Получить решение владельца для затронутой части, параллельно делать независимые задачи |

Задача завершена, когда сквозной путь соответствует критерию, проверки по риску выполнены, ограничения указаны, изменения документации совпадают с diff. При передаче разработчик записывает в КБ ID задачи, ветку и SHA локальных коммитов, состояние, затронутые контракты, критерии приёмки, команды и фактические результаты проверок, ограничения, остаточный риск и ближайший шаг. Ревьюер самостоятельно сверяет diff относительно main, код, контракты и тесты. Существенные исправления возвращает разработчику с конкретными критериями повторного ревью. Небольшие инженерные исправления допустимы с указанием в отчёте. CURRENT_STATE обновлять при смене этапа и существенном блокере. При изменении контракта править его единственный тематический документ и основание в DECISIONS. Состояние подтверждать кодом и тестами.

Чтобы сохранять границы, проводить изменения через штатные операции модуля, не дублировать серверные правила в шаблонах, сохранить один источник решения по доступу. Новую зависимость, новый сервис или межмодульный обход обосновать задачей и стоимостью сопровождения. Начинать с проверки diff и контрактного теста. Общий автоматический архитектурный контроль добавлять при наблюдаемом нарушении.


## GitHub и выпуск

Стабильная main. На значимую задачу ветка вида feat/FIL-12-rating или fix/FIL-34-profile-access. ID брать из задачи GitHub или плана владельца. Коммиты и итоговый squash-заголовок по Conventional Commits, например feat(ratings): добавить быстрое оценивание. Не переписывать опубликованную историю, запретить force push и удаление main. Интеграция через PR, предпочтительно Squash and Merge. При конфликте с опубликованной веткой влить main в ветку и повторить затронутые проверки.

Шаблон PR хранится в [.github/pull_request_template.md](../.github/pull_request_template.md) и включает:

- Задача и критерии приёмки
- Изменения и влияние на поведение
- Фактические команды, результаты, пропуски и причины
- Обновления KB и CHANGELOG
- Миграции, откат и риски, если применимо
- Скриншоты значимых визуальных изменений

Владелец разрешил ревьюеру публиковать рабочие ветки и создавать PR в публичном `FerMaxim/filmoteka`. Перед push ревьюер завершает локальное ревью без блокирующих замечаний и проверяет публикуемые коммиты на секреты и приватные данные. После создания PR ревьюер следит за GitHub Actions, разбирает сбои, сверяет актуальность КБ, CHANGELOG и версий. Существенные исправления CI и реализации разработчик оформляет локальными коммитами и повторно передаёт ревьюеру.

Для merge ревьюер сверяет критерии, разрешение владельца на данный PR или ранее разрешённый объём слияний, отсутствие нерешённых замечаний и успешные обязательные проверки именно текущего head. При смене head проверить снова. Провал, отмена или отсутствие обязательного результата блокируют merge. На GitHub настроить обязательный PR, единый обязательный статус quality-gate и запрет обхода для main, где позволяют права и тариф. При ограниченном тарифе применять тот же регламент вручную и сообщить владельцу об отсутствии технического принуждения. GitHub Free поддерживает защиту для публичных репозиториев, для частных применимы Pro, Team и Enterprise. На этапе подключения проверить видимость, права, активные правила и пробный PR. [GitHub Docs](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

Вести CHANGELOG.md с разделом Unreleased для пользовательских и значимых инженерных изменений. Перед согласованным выпуском перенести записи под версию и дату. SemVer vMAJOR.MINOR.PATCH для Git-тега на проверенном коммите main. Исправления повышают PATCH, совместимые возможности MINOR, несовместимый стабильный контракт MAJOR. Первый номер версии определить по фактической готовности релиза.

## Минимально достаточные проверки

Цель — уверенность в затронутом поведении. Не задавать процент покрытия или квоту тестов. Для существенного исправления бизнес-логики или безопасности добавить воспроизводимый регрессионный тест на самом дешёвом достоверном уровне. Не подгонять корректные ожидания под дефект.

| Риск | Проверка |
|---|---|
| Формула | Unit на отсутствие критериев, ноль, крайние и частичные наборы, согласованную границу округления |
| Записи, доступ, импорт | Интеграция через HTTP и PostgreSQL, чужой объект, лишние поля, ограничения, откат и две конкурентные записи через отдельные соединения |
| Основные пользовательские пути | Playwright на синтетических данных. Оценить и перечитать, порекомендовать и открыть профиль в отдельной сессии с согласованными правами |
| Доставка | Smoke запускает собранный контейнер, ждёт readiness с таймаутом, открывает основные доступные страницы и подтверждает работу с БД |
| Интерфейс | Браузер на мобильной и широкой ширине. Проверить клавиатуру, фокус, контраст, reduced motion, отсутствие перекрытий, горизонтального скролла и JS-ошибок. Сохранить скриншоты для PR |

Контракт команд этапа фундамента — один Python-диспетчер tools/check.py, одинаковый в контейнере и Actions:

| Команда | Что выполняет |
|---|---|
| python tools/check.py target <pytest-node-id> | Один модуль или сценарий |
| python tools/check.py quick | Ruff lint/format check, Django check, отсутствие незаписанных миграций и pytest-сценарии с меткой quick. Django использует dummy backend, поэтому проверка истории миграций PostgreSQL здесь отсутствует |
| python tools/check.py full | Проверки кода и истории миграций в тестовом стеке, миграции с нуля, вся коллекция pytest за один прогон, HTTP smoke и Playwright |
| python tools/check.py browser | Playwright и снимки выбранных экранов |
| python tools/check.py smoke | Запуск и проверка одноразового стека |
| python tools/check.py docs | Локальные ссылки и целостность изменённых инструкций |

В разработке запускать target. Перед PR quick и проверки затронутого риска. Для документации достаточно docs, для чистого CSS браузерная проверка и имеющиеся проверки стилей. Перед merge малый быстрый набор выполнять целиком в CI, изменения доступа, БД и форм требуют интеграционных проверок. Перед релизом обязателен full. Отчёт содержит команды, длительность, фактические количества прошедших, пропущенных и упавших тестов, код завершения. Для нетестовой команды указывать её результат. На успехе выводить сводку, на сбое — имя проверки и релевантный фрагмент. Возвращать исходный ненулевой код дочерней команды. Полный очищенный лог сохранять как артефакт с ограниченным сроком. Переиспользовать результат при идентичных входах, включая настройки и зависимости. Успешные логи не требуют ИИ-ревью.

## Изоляция и миграции

Для каждого запуска с БД создать отдельный Compose project или изолированный CI service PostgreSQL той же версии, одноразовый том, отдельный случайный пароль и тестовую роль. У тестового контейнера нет production-секретов и маршрута к production. До подключения, migrate, очистки или создания БД диспетчер требует test settings, точное ожидаемое имя хоста тестового сервиса, имя БД и роли данного запуска. Запрещены наследование рабочего DATABASE_URL и запасной адрес. После подключения сверить current_database(), current_user и маркер запуска, созданный при инициализации тестового кластера. При несовпадении немедленно завершиться с ошибкой. Для pytest-django согласовать имя фактической TEST.NAME с этой проверкой. Уничтожать только ресурсы своего запуска. Приёмка включает безопасный тест отказа на подставном неподходящем адресе без обращения к нему. Интеграции используют синтетические данные и заглушки внешних API.

В тестовом стеке PostgreSQL при инициализации создаёт базу данного запуска. Диспетчер применяет штатные миграции. Фикстура pytest-django подключается к готовой базе, а тесты используют изоляцию Django. Удалением одноразового хранилища управляет Compose. Тестовый backend проверяет параметры до вызова драйвера и идентичность каждого нового соединения до SQL приложения. Это распространяется на проверку истории, миграции, pytest и тестовый web.

Миграции версионируются рядом с моделями. Проверять чистую установку и переход с предыдущей схемы. Предпочитать добавление совместимого поля, перенос данных, переключение чтения, затем отдельную очистку. До разрушительной миграции — явное согласование, резервная копия, проверенное восстановление на отдельной БД и план возврата приложения к совместимой схеме.

## Безопасность

ORM и параметры для SQL, сортировки и изменяемые поля по разрешённому списку. На сервере проверять диапазоны, длины, типы и принадлежность объекта, брать owner из сессии. Приватные запросы ограничивать владельцем прямо в queryset. Профиль выдаёт только разрешённые поля. Проверять матрицу гость / владелец / другой пользователь. Итоговый балл от клиента не принимать.

Использовать стандартные Django authentication, password hashers, валидаторы и ротацию сессии. Для всех изменяющих запросов с cookie обязательны CSRF middleware и token, в production HTTPS, secure cookies, HttpOnly для сессии, SameSite, ALLOWED_HOSTS, DEBUG=False. Экранировать пользовательский текст средствами шаблонов, вставлять в DOM как текст. Ограничивать размер запросов, пагинацию, частоту входов и дорогих запросов на доверенном ingress, с ответом 429. Не доверять произвольным forwarded-заголовкам. До включения загрузок определить допустимые типы, проверять содержимое и размеры, перекодировать изображения и выдавать со случайными именами из изолированного хранилища.

Секреты инъецируются средой, .env исключён из Git и Docker context. Не логировать cookie, ключи и личные комментарии. Роль приложения имеет только необходимые права, DDL — у роли миграций. Зависимости и Actions фиксируются, обновления проходят CI и проверку известных уязвимостей. Утечка требует отзыва ключа. Внешние вызовы ограничены правилами [архитектуры](ARCHITECTURE.md).

## Docker и CI

Windows 11, Docker Desktop в режиме Linux containers, Compose v2. Базовый compose.yaml содержит web и db, dev override добавляет bind mount и публикует только 127.0.0.1:8000. У PostgreSQL внутренний порт, именованный постоянный volume для dev, отдельный для production. В production Gunicorn, собранная статика через WhiteNoise, HTTPS на ingress площадки. Миграции одноразовой командой до запуска новой версии. Healthchecks — pg_isready у БД, HTTP readiness у web.

Dockerfile многостадийный. Builder устанавливает из uv.lock в frozen-режиме, runtime содержит только окружение выполнения и приложение, работает с непривилегированным UID. Отдельный test target с dev-зависимостями и совпадающей версией браузера Playwright. На фундаменте зафиксировать точные patch-теги и digests Python 3.13 slim и PostgreSQL 17, версию uv и lock, проверить сборку обоих targets. .env.example содержит имена переменных и безопасные локальные примеры, секреты обязательны при запуске. Контракт запуска из PowerShell — docker compose up -d --build, штатная остановка docker compose down сохраняет dev-данные.

Actions на pull_request и перед выпуском. Кэш пакетов по ОС, версии Python и lock-файлу, BuildKit cache для образа. Минимальные permissions contents: read, сторонние actions закреплены по SHA. Для PR concurrency по номеру PR с cancel-in-progress. Плановые лимиты 10 минут quick и 25 минут integration/browser, уточнить по замерам. Классификатор путей внутри всегда запускаемого workflow выбирает наборы, неизвестный путь требует полной проверки. Итоговый quality-gate запускается даже после сбоя зависимости, проверяет результаты всех назначенных наборов, допускает skip только для заведомо нерелевантных. Браузер запускается против изолированного web и test-db. Docker smoke оркестрируется с runner без передачи Docker socket приложению. Для локального full тот же диспетчер на хосте поднимает Compose и делегирует наборы в test target. Перед релизом проверяются все наборы, запуск образа и восстановление после изменения схемы.

## Эксплуатация рабочей среды

- **Среды и доступ.** Рабочие секреты и данные отделены от разработки и CI. Публикуется HTTPS-вход через прокси, PostgreSQL и Gunicorn доступны по закрытой сети. Проверить production settings командой Django check --deploy. Административные операции выполняются с отдельными полномочиями. До запуска проверить сценарий доступа к аккаунту и восстановления доступа, применимый к согласованной регистрации. [Django deployment checklist](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/)
- **Резервирование.** Исходный вариант — ежедневная автоматическая зашифрованная копия PostgreSQL во внешнее хранилище. Защита нужна также для невоспроизводимых файлов, если они появятся, и для доступа к конфигурации восстановления через защищённый канал. Следить за возрастом последней успешной копии. До запуска восстановить копию в чистой изолированной среде и проверить вход и чтение контрольных записей. Повторять учение после существенного изменения схемы или механизма копирования. Периодичность и хранение согласовать с допустимой потерей данных и сроком восстановления. Базовая схема с суточным интервалом допускает потерю изменений между копиями. [Документация PostgreSQL](https://www.postgresql.org/docs/17/backup.html)
- **Обновления.** Выпускать проверенный образ с фиксированным идентификатором. Согласовать короткое окно обслуживания при несовместимой миграции. Проверить свежую копию, применить миграции, запустить новую версию и smoke через HTTPS. При сбое вернуть предыдущий образ, если схема совместима. Для несовместимой схемы использовать заранее проверенный план миграции вперёд или восстановления. Учитывать потерю записей после точки восстановления.
- **Наблюдаемость.** Настроить внешнюю проверку доступности и уведомления о недоступности, всплеске ошибок, нехватке места и просроченной копии. Хранить ограниченные по объёму журналы без секретов и пользовательского текста. Назначить получателя уведомлений. Проверить, что есть доступ к конфигурации, предыдущему образу и внешним копиям при потере основного хоста.
