# Работа с КБ и передача задач

## Старт задачи

Выбери выделенный ID в [BACKLOG](BACKLOG.md) и выполни `python tools/task.py start T-007` из своей рабочей копии. Прочитай задачу, указанную спецификацию и нужные разделы контрактов по [указателю](README.md). Критерии проверок — в [ENGINEERING](ENGINEERING.md).

Команда сверяет ветку, HEAD, рабочее дерево, локальный origin/main и опубликованные Git refs, показывает расхождение с main и известные рабочие копии задачи. Ветка новой задачи должна содержать ID отдельным сегментом (например, `codex/T-007-library`). Для уже выделенной ветки с другим именем её можно указать в реестре в виде `Ветка \`codex/harness-2\``. Поиск копий опирается на имена веток и каталогов, в том числе в других зарегистрированных worktree. При расхождениях, блокировке или недоступной базе сверить источники до начала реализации. `--offline` показывает состояние по локальным refs; свежесть базы остаётся неподтверждённой. Код 0 означает отсутствие обнаруженных расхождений, 1 требует сверки, 2 означает ошибку входа или проверки.

Ревьюер резервирует разные ID строками BACKLOG перед параллельной передачей. ID сохраняется в ветке, handoff и PR, дополнительные внешние ID можно указать в примечании. При коллизии сохранить работу и передать её ревьюеру. ID выделяется один раз.

## Реестр задач

Каждая задача занимает одну строку:

```text
- [ ] T-NNN Название | стадия | выкладка | блокировка | спецификация | задача или доказательства
```

Для простой задачи укажи `—` в поле спецификации и опиши критерий в последнем поле. Для сложной укажи Markdown-ссылку на `TASKS/T-NNN.md` и используй [шаблон](TASKS/TEMPLATE.md). Поля разделяет `|`, в полях используй обычное тире или запятые. При наличии блокировки укажи причину и нужное действие, иначе `нет`.

Стадии: `запланировано → в работе → на ревью → принято → интегрировано`. Ревьюер возвращает задачу в `нужны исправления`, разработчик возвращает её в `на ревью`. Отмена получает `отменено` и основание. Чекбокс `[x]` используют для `интегрировано` и `отменено`; остальные стадии используют `[ ]`.

Выкладка ведётся отдельно: `не требуется`, `не запланирована`, `ожидает`, `выполнена`, `откачена`. Агент эксплуатации фиксирует установленный SHA и проверки в отчёте, обновляет выкладку в BACKLOG и факты о среде в [OPERATIONS](OPERATIONS.md).

## Передача работы

Обнови строку BACKLOG при передаче, возврате, блокировке, приёмке, интеграции, выкладке или откате. Спецификация хранит цель, критерии, доказательства и следующий шаг. На передачу укажи проверенный SHA, фактические проверки, ограничения и ближайшее действие. При интеграции сохрани SHA main, исходный head, PR и CI. Существенные замечания ревьюер возвращает с критериями повторной проверки. Обнови затронутый контракт и запиши основание значимого решения в [DECISIONS](DECISIONS.md).

Для передачи можно задать `FILMOTEKA_CHECK_REPORT` на новый файл вне worktree перед запуском `python tools/check.py full`, затем выполнить `python tools/task.py handoff T-009 --report <путь>` из чистой копии с реализацией. Команда выводит ветку, SHA и строки отчёта. Сверь отчёт с SHA, для которого его получили, и добавь результаты тестов и ограничения из сводки. Перед публикацией проверь отсутствие секретов и закрытых данных.

`python tools/check.py docs` проверяет реестр, спецификации, локальные ссылки, якоря и ID решений. При расхождении сверяй Git, фактические проверки и последнее прямое решение владельца. Отчёты с прошедших этапов относятся к указанным в них SHA и средам.
