# Работа с КБ и передача задач

## Старт задачи

Выбери выделенный ID в [BACKLOG](BACKLOG.md) и выполни `python tools/task.py start T-007` из своей рабочей копии. Прочитай задачу, указанную спецификацию и нужные разделы контрактов по [указателю](README.md). Критерии проверок — в [ENGINEERING](ENGINEERING.md).

Команда сверяет ветку по ID задачи или явному alias из примечания ``Ветка `codex/harness-2```, HEAD, рабочее дерево, базу и доступные записи задачи на main и известных ветках. Разработка ведётся в выделенной ветке. При расхождениях, блокировке реализации или неподтверждённой базе сначала сверить источники. Отсутствующая запись или прежний формат помечаются как неполные сведения. Команда видит Git refs и зарегистрированные worktree по ID или alias. Другие клоны и чаты требуют отдельной сверки. `--offline` показывает локальные данные без подтверждения свежести. Код 0 означает отсутствие обнаруженных блокирующих расхождений, 1 требует сверки, 2 означает ошибку входа или проверки.

Ревьюер резервирует разные ID строками BACKLOG перед параллельной передачей. ID сохраняется в ветке, handoff и PR, дополнительные внешние ID можно указать в примечании. При коллизии сохранить работу и передать её ревьюеру. ID выделяется один раз.

## Реестр задач

Каждая задача занимает одну строку:

```text
- [ ] T-NNN Название | стадия | ответственный | выкладка | блокировка | спецификация | задача или доказательства
```

Для простой задачи укажи `—` в поле спецификации и опиши критерий в последнем поле. Для сложной укажи Markdown-ссылку на `TASKS/T-NNN.md` и используй [шаблон](TASKS/TEMPLATE.md). Поля разделяет `|`, в полях используй обычное тире или запятые. Ответственный — `разработчик`, `ревьюер` или `эксплуатация`. Блокировка задаётся как `реализация: причина и действие`, `приёмка: причина и действие` или `выкладка: причина и действие`. Несколько областей разделяются сочетанием точки с запятой и пробела. При отсутствии блокировок укажи `нет`. Старт учитывает блокировку реализации, остальные показываются для соответствующих стадий.

Стадии: `запланировано → в работе → на ревью → принято → интегрировано`. Ревьюер возвращает задачу в `нужны исправления`, разработчик возвращает её в `на ревью`. Отмена получает `отменено` и основание. Чекбокс `[x]` используют для `интегрировано` и `отменено`; остальные стадии используют `[ ]`.

Выкладка ведётся отдельно: `не требуется`, `не запланирована`, `ожидает`, `выполнена`, `откачена`. Агент эксплуатации фиксирует установленный SHA и проверки в отчёте, обновляет выкладку в BACKLOG и факты о среде в [OPERATIONS](OPERATIONS.md).

## Передача работы

Обнови строку BACKLOG при передаче, возврате, блокировке, приёмке, интеграции, выкладке или откате. Спецификация хранит цель, критерии, доказательства и следующий шаг. На передачу укажи проверенный SHA, фактические проверки, ограничения и ближайшее действие. При интеграции сохрани SHA main, исходный head, PR и CI. Существенные замечания ревьюер возвращает с критериями повторной проверки. После изменения кода ревьюер повторно проверяет затронутый риск на новом SHA до интеграции. Полномочия на публикацию, PR и merge закреплены в [ENGINEERING](ENGINEERING.md). Обнови затронутый контракт и запиши основание значимого решения в [DECISIONS](DECISIONS.md).

Для передачи создай новый путь вне worktree и задай `FILMOTEKA_CHECK_REPORT` перед запуском `python tools/check.py full` на чистом коммите. Отдельный файл нужен для каждого запуска. `python tools/task.py handoff T-009 --report <путь>` сверяет итог набора, завершённость, SHA и чистоту дерева в начале и конце прогона. Для изменения, которому ENGINEERING назначает только документационную проверку, укажи `--suite docs` и передай соответствующий отчёт. Старые текстовые отчёты остаются историческими. Снимки Git отражают состояние в начале и конце проверки, включая незакоммиченные и неигнорируемые файлы. Во время прогона рабочую копию следует оставить неизменной. Добавь количество тестов и ограничения из сводки, перед публикацией проверь отсутствие секретов и закрытых данных.

`python tools/check.py docs` проверяет реестр, спецификации, локальные ссылки, якоря и ID решений. При расхождении сверяй Git, фактические проверки и последнее прямое решение владельца. Отчёты с прошедших этапов относятся к указанным в них SHA и средам.
