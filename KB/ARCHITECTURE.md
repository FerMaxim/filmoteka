# Архитектура Filmoteka · утверждена владельцем 24 ноября 2026

Основание — [P01–P16 и U01–U09](PRODUCT.md). Один браузерный клиент, одна база, короткие операции над коллекцией одного владельца. Приняты один веб-сервис и одна PostgreSQL. Сессии в БД позволяют масштабировать web отдельно при появлении нагрузки.

## Выбор стека

Модульный монолит описывает границы домена и деплоя. Любой вариант ниже позволяет собрать монолит. В вариантах с React разница для Sol состоит в количестве рабочих контрактов между браузером, HTTP и сервером. Маски, слои, адаптивные изображения и композитные переходы доступны всем четырём вариантам средствами браузера. Оценки сложности основаны на сценариях KB, измерений на прототипе пока нет.

Утверждённый стек для долгосрочной эксплуатации — **Django с шаблонами, CSS и ES-модулями**. Гипотеза для проверки — доступная форма оценивания со всеми согласованными состояниями остаётся локальным компонентом, профиль и каталог рендерятся на сервере. Если прототип покажет хрупкую синхронизацию состояний между независимыми частями экрана или появится согласованный отдельный клиент, пересмотреть сначала конкретный компонент или HTTP-контракт. SQLite проще для однопользовательского сценария, но в Django select_for_update на SQLite не действует. PostgreSQL запускается отдельным процессом и требует применения миграций. Для тысяч карточек достаточно пагинации и запроса по локальному каталогу. Измерить поиск на представительном объёме перед добавлением pg_trgm или отдельного поисковика.

## Границы модулей и утверждённый стек

Python 3.13, Django 5.2 LTS, psycopg 3 и PostgreSQL 17. ORM, формы, сессии, авторизация, миграции и шаблоны входят в один фреймворк. SQL-ограничения и транзакции PostgreSQL нужны для конкурентного редактирования коллекции. HTML на сервере, CSS custom properties, небольшие ES-модули для интерактивности. Тестовый стек — pytest, pytest-django и Python Playwright. Зависимости фиксировать в uv.lock. [Поддержка Django](https://www.djangoproject.com/download/) · [Поддерживаемые БД](https://docs.djangoproject.com/en/5.2/ref/databases/)

| Путь будущего приложения | Ответственность |
|---|---|
| config/ | URLs, WSGI и настройки разработки и тестов. Настройки рабочей среды определяются перед выкладкой |
| accounts/ | Пользователь на основе AbstractUser, сессии, стабильная ссылка на профиль и политика видимости |
| catalog/ | Карточка произведения, поиск в локальном каталоге, команда импорта |
| collection/ | Связь пользователя с произведением, флаги, оценки, эмоции, рекомендации, выборки вкладок |
| templates/, static/ | Общий каркас, компоненты форм, карточек и навигации, токены, стили, интерактивность |
| tests/e2e/, tools/, .github/ | Межмодульные сценарии, единая точка запуска проверок, CI |

View связывает HTTP с формой и операцией модуля. Операция получает действующего пользователя от сервера, валидирует команду и выполняет транзакцию. Функция расчёта в collection одна для всех экранов. Выборка профиля применяет политику accounts до сериализации или рендера. Модули вызывают функции внутри процесса. Отдельные очереди, Redis, поисковый движок и внешний API-клиент в браузере при текущих сценариях и ожидаемой нагрузке не требуются.

Зависимости идут от config и HTTP-слоя к модулям. accounts и catalog самостоятельны, collection обращается к их моделям и явно названным операциям чтения. Сборка страницы профиля использует политику accounts и выборку collection в HTTP-слое. Шаблоны получают готовые данные, приватность не задаётся CSS или JavaScript. Формула и операции записи имеют одну точку входа. Межмодульные изменения проверять по HTTP-контракту и затронутому риску. Для обнаружения циклов начинать с ревью импортов, добавлять автоматическое архитектурное ограничение при повторении проблемы.

## Рабочая серверная архитектура

Будущая цель — сервис для небольшой аудитории с постоянными аккаунтами, оценками и рекомендациями. Сохранность данных, управление доступом и воспроизводимое обслуживание входят в требования первой рабочей версии. Docker и Compose не используются, включая будущую рабочую среду. Подготовку сервера, нативную выкладку и обслуживание выполняет третий агент эксплуатации по [OPERATIONS](OPERATIONS.md). Площадка, способ управления процессами и настройки production определяются отдельной задачей по решению владельца.

Кандидат для будущего размещения — один Linux-хост с HTTPS-входом, Django и PostgreSQL по закрытой сети. Резервные копии хранятся за пределами хоста. Одиночный узел предполагает простой при отказе и допускает краткое окно обслуживания. Перед запуском утвердить площадку, способ запуска процессов приложения, отдачу статики и требования к сроку восстановления. Управляемую PostgreSQL можно подключить с тем же контрактом приложения, если условия обслуживания и хранения данных это оправдают.

Плановые импорты каталога выполняются отдельной командой того же приложения. Планировщик хоста может запускать её при подтверждённой необходимости. При проблемах сначала измерять задержки, запросы, соединения БД, ресурсы и время импорта. Дополнительный web-узел, управляемая БД или отдельный фоновый исполнитель рассматриваются при подтверждённом узком месте или требовании доступности. Правила резервирования, обновления и приёмки находятся в [регламенте эксплуатации](ENGINEERING.md#эксплуатация-рабочей-среды).

## HTTP-контракт браузера

| Метод и маршрут | Вход и результат |
|---|---|
| GET /catalog/ и /works/{id}/ | Параметры q и page для поиска по названию, ограниченная страница результатов, детали по внутреннему ID |
| POST /accounts/login/ и /accounts/logout/ | Стандартные Django views с CSRF, установка или завершение серверной сессии |
| GET /me/library/ | Только владелец, пагинация, независимые признаки записей |
| POST /me/works/{id}/library/ | Явные целевые значения изменяемых флагов, пропущенный флаг сохраняется |
| POST /me/works/{id}/rating/ | Полная форма оценки, версия записи, список тегов, комментарий. Сервер вычисляет итог |
| POST /me/works/{id}/recommendation/ | Явная рекомендация и отдельное описание. Допустимость без оценки требует решения |
| GET /p/{public_id}/rated/ и /p/{public_id}/recommendations/ | Две отдельные пагинированные выборки, только разрешённые посетителю поля |
| GET /health/live и /health/ready | Жизнеспособность процесса и готовность обслуживать запрос с проверкой БД, без внутренних подробностей |

Успешная запись → 303 на GET. Ошибка формы → 422 с сохранением ввода. Для защищённых HTML-страниц гость переходит ко входу. Для недоступного объекта — 404, при конфликте версии — 409 с предложением перечитать запись. GET не изменяет данные. Публичный JSON API пока не нужен. Удаление пользовательской записи и публикация полей получают маршруты после согласования поведения.

## Реляционная модель

Внутренние PK — bigint, если ниже не задан общий ключ с родителем. FK обязательны, кроме явно опциональных полей. Время в UTC.

| Таблица | Ключи, значения и ограничения |
|---|---|
| user | Стандартные поля Django, уникальный логин, public_id UUID UNIQUE для постоянной ссылки. Способ регистрации определяется до запуска |
| work | id, title, kind. Название непустое, тип из поддерживаемого справочника, заголовок сам по себе не уникален |
| external_ref | id, work FK, provider, external_id. UNIQUE(provider, external_id) обеспечивает повторяемый импорт |
| entry | id, owner FK, work FK, added, watched, want_to_watch, favorite — независимые boolean, version ≥ 1. UNIQUE(owner, work). Техническая связь сама по себе не выставляет пользовательские флаги |
| rating | entry_id одновременно PK и FK, impression обязателен, семь nullable NUMERIC по именам критериев из PRODUCT, comment. Для каждого числа CHECK от 0 до 10. Значение NULL означает пропуск. Итог вычисляется из входов, точность хранения позволяет согласовать шаг отдельно |
| emotion, rating_emotion | emotion.id, уникальный стабильный code, label. Связь с двумя FK и UNIQUE(rating_id, emotion_id). Разрешённые теги валидирует сервер |
| recommendation | entry_id одновременно PK и FK, description, created_at. Самостоятельная запись для вкладки рекомендаций |

Быстрая оценка создаёт rating с одним впечатлением. При подробной оценке считать среднее в decimal, округлять итог при выводе. Теги и текст сохраняются в той же транзакции. Порядок при точной половине, шаг, правила очистки и переходов согласовать перед реализацией формы. Просмотр не выводится из наличия оценки.

Запись блокирует entry внутри atomic, создание опирается на UNIQUE пары и повторное чтение после конкурентной вставки. Сравнить версию под блокировкой, обновить поля и увеличить версию один раз. Повтор уже применённой команды с той же версией может получить 409, дубликат исключён. Сбой откатывает и теги, и оценку. Удаление пользователя каскадно удаляет личные строки, удаление entry — дочерние данные. Удаление work с пользовательскими записями запрещено (PROTECT), справочные эмоции в употреблении также защищены. Физическое удаление данных пользователя требует согласованного сценария. Начать с PK, UNIQUE и индексов FK Django, не дублировать их. Для нового индекса предъявить запрос и EXPLAIN на представительном объёме.

## Каталог и внешние зависимости

По R36 от 25 ноября 2026 владелец выбрал **Kinopoisk API Unofficial**, общий локальный каталог, поиск с общим кешем и импорт выбранного ID по требованию. TMDB в текущем коде и утверждённой КБ не было; заменять действующую интеграцию не требуется. Первоначальные синтетические fixtures сохраняются для автономной разработки и CI.

[Проект интеграции каталога](CATALOG.md) сопоставляет отчёт с кодом, описывает расширение work/external_ref, person/credit/poster, общий поисковый кеш/lease/ограничитель, сервисы и сценарии. **Выбор поставщика принят; детальная схема и параметры находятся на согласовании.** Реализация и карточка программисту пока не поручены.

catalog хранит общие метаданные без владельца; collection хранит личные оценки, комментарии, статусы и рекомендации отдельно. Внешние рейтинги не являются личным итогом. В T-005 реализованы accounts.User, catalog.Work и collection.Entry; остальные строки таблицы остаются архитектурным планом, расширяемым проектом CATALOG. Принятые контракты entry/rating и формула не изменяются.

Браузер вызывает только Django. Локальное чтение библиотеки/оценок не обращается к API; внешний поиск кеширует компактных кандидатов отдельно от постоянных work. Явное добавление импортирует только выбранный внешний ID с дедупликацией по external_ref, не по названию. Поисковый GET не создаёт work/entry; предложенные POST импорта и добавления, конкурентность и частичные данные — в CATALOG. HTTP не выполняется под долгой SQL-транзакцией. Management command используется для ограниченного refresh; Redis/Celery/новый сервис не требуются.

До публичной эксплуатации подтвердить права и сроки хранения/показа метаданных и posterUrl, атрибуцию, тариф и production-доступ. Разрешён только основной постер, остальные изображения и сезоны вне MVP. Ключ в окружении; таймауты, квоты, SSRF-проверки и деградация обязательны. Локальный каталог и личные данные остаются доступны при ошибке поставщика. Предложение Storage/кеша/моделей и план миграций не считаются выполненным кодом.
По R45 на этапе 4 гостевой профиль использует серверную выборку только полей из [политики видимости](PRODUCT.md#профиль-по-ссылке--r45). Личная библиотека и любые изменения остаются защищены сессией владельца. Самостоятельная регистрация отложена за рамки MVP.


## Фотография фона · предложение для следующего серверного этапа (T-003 / R33)

В прототипе `/prototype/` выбирается локальный файл и показывается до перезагрузки; отправки и серверного хранения нет. Для рабочей версии предлагается расширить accounts полем ссылки на обработанный файл фона и добавить owner-only POST установки/сброса с CSRF, формой и 303 после успеха; публичное чтение допускается только после определения политики видимости. Владелец берётся из сессии, идентификатор владельца из запроса не принимается. Гость направляется на вход, другой пользователь не может менять чужой фон. Сброс обнуляет ссылку и восстанавливает единый стандартный фон.

До реализации согласовать численные лимиты байт/пикселей и форматы. Проверять не только MIME/расширение, но декодировать изображение, ограничивать размеры и ресурс декодирования, перекодировать без метаданных в разрешённый растровый формат; SVG и произвольный HTML не выдавать как пользовательские изображения. Имена случайные, хранение вне исполняемых static/templates; удаление старого файла после успешной транзакции, без удаления чужих/общих файлов. Обработка потребует обоснованной зависимости для декодирования (возможный Pillow); она пока не добавлена. Тесты будущей реализации: гость/владелец/другой пользователь, CSRF, неверный MIME и содержимое, превышение лимитов, повторная установка, сброс, отсутствие метаданных, сбой записи с сохранением предыдущего фона; БД только изолированная по ENGINEERING. Это проектирование, не реализованная серверная функция и не утверждённые ограничения из HTML.


## Реализация этапа 2а · T-005

Accounts.User наследует AbstractUser, сохраняет физическое имя auth_user и прежние PK/пароли/группы/права/сессии при обновлении. AdoptUser в первой миграции создаёт таблицу на чистой схеме либо расширяет прежнюю auth_user: id до bigint, уникальный public_id UUID для каждой строки; content type auth.user переносится в accounts.user с сохранением permission ID. Всё в атомарной миграции. Обратная миграция accounts намеренно запрещена, чтобы не удалить пользователей; откат требует отдельно проверенного плана сохранения данных. Рабочая dev-база для проверки не используется.

Реализованы защищённые GET /catalog/ (q до 300 символов, 24 результата на странице), /works/{id}/ и /me/library/. Catalog.Work содержит title/kind и серверные ограничения. Общие метаданные не имеют owner. POST /me/works/{id}/library/ принимает только added=true и CSRF; owner берётся из сессии. Лишние поля отклоняются с 422. Это единственная команда признаков этапа: устанавливает added, сохраняет watched/want_to_watch/favorite. Entry по умолчанию имеет все признаки False, UNIQUE(owner, work), version >= 1. Atomic/get_or_create и блокировка строки обеспечивают повторяемое добавление; версия растёт только при изменении added. Недоступная работа — 404, успех — 303, GET не пишет.

/accounts/login/ и /accounts/logout/ используют стандартную Django authentication; серверные сессии, ротация при входе, выход только POST с CSRF, ошибки входа 422, успех 303. Гости направляются ко входу, вся библиотечная выборка ограничена request.user. Маршрутов чтения/изменения entry по чужому owner/entry ID нет. Публичные профили, регистрация, оценивание и остальные команды признаков на сервере не реализованы.

Серверный сценарий доступен из кнопок каталога/библиотеки главной. /prototype/ остаётся синтетическим визуальным прототипом с временными оценками/фото; он не используется как источник серверных данных. Kinopoisk/external_ref и прочие расширения этапа 2б не реализуются здесь.
